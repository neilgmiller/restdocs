# Milestone v1.0: asyncResponse Block Support

**Status:** ✅ SHIPPED 2026-06-09
**Phases:** 1–3
**Total Plans:** 5

## Overview

Added first-class `asyncResponse` support to the restdocs toolchain in three phases:
storage/domain/validation foundation (Phase 1), Kotlin code generation (Phase 2), and
HTML rendering (Phase 3). Any method that returns a job ID can now declare its eventual
async payload in the same spec entry — visible in generated HTML docs and typed Kotlin client code.

## Phases

### Phase 1: Storage Model + Validation Foundation

**Goal:** YAML specs with `asyncResponse` blocks parse, map through the full pipeline, and are validated with the same rigor as `response` blocks
**Depends on:** Nothing (first phase)
**Plans:** 3 plans

Plans:

- [x] 01-01: Add asyncResponse field to storage.Method, domain.Method, and wire StorageToDomainMappers
- [x] 01-02: Thread warningEmitter through Validatable, ValidationModule, ValidatingBeanDeserializerModifier, ValidatingDeserializer, createMapper
- [x] 01-03: Implement VALID-03/VALID-04 cross-field validation in storage.Method and wire DocValidator

**Success Criteria (all met):**
1. A YAML method entry containing an `asyncResponse` block parses without error (no UnrecognizedPropertyException)
2. After parsing + mapping, `domain.Method.asyncResponse` is non-null for methods that declare the block and null for methods that do not
3. A YAML method with a malformed `asyncResponse` produces a validation error with field path
4. A YAML method with `asyncResponse` but no `job` field in `response` produces a validation error
5. A YAML method whose `response` contains a `job` field but has no `asyncResponse` produces a validation warning

**Completed:** 2026-06-02

---

### Phase 2: Kotlin Code Generation

**Goal:** The Kotlin generator emits typed `*AsyncResponse` data classes alongside existing `*Response` classes for methods with async payloads
**Depends on:** Phase 1
**Plans:** 1 plan

Plans:

- [x] 02-01: Extend MethodProcessor to emit *AsyncResponse data classes, fix MethodClassNames, unit test + smoke test

**Success Criteria (all met):**
1. Running `kotlin_generator` on a spec with a method that has `asyncResponse: { type: object, fields: [...] }` produces a `*AsyncResponse` data class file
2. The generated `*AsyncResponse` class contains properties matching the fields declared in the `asyncResponse` block
3. Methods without an `asyncResponse` block produce no `*AsyncResponse` class (no regression)

**Completed:** 2026-06-05

---

### Phase 3: HTML Rendering

**Goal:** Generated HTML documentation displays async response payloads in a clearly labelled section beneath the immediate response
**Depends on:** Phase 1
**Plans:** 1 plan

Plans:

- [x] 03-01: Extend rest_api_doc.vm with asyncResponse section + DocGeneratorAsyncHtmlTest

**Success Criteria (all met):**
1. The rendered HTML for a method with `asyncResponse` contains a second response section visually distinct from the immediate response
2. The section heading reads "Async Response (via getAsyncJobStatus)" with a prose note explaining that content appears in `jr` when `jobStatus` is `0`
3. The async response field table uses the same visual treatment as the immediate response table
4. Methods without `asyncResponse` render identically to before (no regression)

**Completed:** 2026-06-09

## Milestone Summary

**Key Decisions:**

- asyncResponse reuses existing `Response` type verbatim — no new types needed
- Jackson 3.x FAIL_ON_UNKNOWN_PROPERTIES is true and NOT overridden — adding the storage field is the whitelist
- VALID-04 gates on `!AccumulatingContext` to avoid false positives during first-pass accumulation
- `responseIsAsync()` checks both typeRef membership and inline `job` field name for full coverage
- TypeRefSpec asyncResponse produces no `*AsyncResponse` class in codegen (D-01 — no fields to emit)
- Template iterates `Service.methods` flat list as `$method` objects (Resource hierarchy does not exist in storage model)
- Replaced stub Velocity template with canonical live template from allego1.0 — stub had diverged too far (wrong loop variable, missing sidebar nav, broken response rendering)

**Issues Resolved:**

- Pre-existing `FieldElementListIncludeOnlyTest.kt` compilation failure (unresolved `DataSpec` reference) fixed during Phase 1 work
- `@TempDir` lateinit initialization order issue with `@TestInstance(PER_CLASS)` + `@BeforeAll` — replaced with `Files.createTempDirectory()` in `@BeforeAll`
- Template double-loop bug (inner `$resource.actions` loop never executing) — resolved by replacing with canonical live template

**Issues Deferred:**

- Migrating 49 existing `AsyncCapableResponse` usages to new format (opportunistic, no urgency)
- Hyperlink cross-linking from asyncResponse sections to `getAsyncJobStatus` method entry
- Formal JSON Schema / grammar update for the YAML format
- `jr` field cross-referencing per method
- `AsyncJobResponse` canonical typeref definition formally in the spec

**Technical Debt:**

- None incurred — clean layered implementation following existing patterns throughout
