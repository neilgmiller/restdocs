## v1 Requirements — Final Status

### Foundation (storage/domain/mapper)

- [x] **FOUND-01**: The storage `Method` model has a nullable `asyncResponse` field that Jackson deserializes from YAML — YAML files containing `asyncResponse` parse without error
- [x] **FOUND-02**: The domain `Method` model has a nullable `asyncResponse` field of type `domain.Response` — downstream consumers can read the field
- [x] **FOUND-03**: `StorageToDomainMappers` wires `asyncResponse` from storage to domain, applying the same type resolution as `response` — the full storage→domain pipeline is connected

### Validation

- [x] **VALID-01**: `asyncResponse` is recognized as a valid method-level YAML key — the validator does not flag it as an unknown field
- [x] **VALID-02**: The same structural rules that apply to `response` apply to `asyncResponse` — malformed async blocks are caught at validation time
- [x] **VALID-03**: The validator emits a warning when a method's `response` contains a `job` field but the method has no `asyncResponse` block
- [x] **VALID-04**: The validator emits an error when a method has an `asyncResponse` block but its `response` does not contain a `job` field

### HTML Rendering

- [x] **HTML-01**: The rendered HTML for a method with `asyncResponse` includes a clearly labelled second response section beneath the immediate response
- [x] **HTML-02**: The second response section heading is **"Async Response (via getAsyncJobStatus)"** with a prose note about `jr` / `jobStatus`
- [x] **HTML-03**: The async response section renders field tables using the same visual treatment as the immediate response section

### Kotlin Code Generation

- [x] **CODEGEN-01**: `kotlin_generator` emits a `*AsyncResponse` data class for each method that has an `asyncResponse` block
